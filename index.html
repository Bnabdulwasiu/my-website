Featured Project Deep Dive

Append-Only Event Store (Database WAL Engine)

This project explores the core durability principles of databases like PostgreSQL. Instead of modifying files in-place (which risks fatal corruption upon crash), it implements an immutable write-ahead log system with in-memory indexes.

The Problem It Solves

Modifying a database file in-place overwrites active bytes on disk. If the server crashes or loses power halfway through, both the previous data and the incoming update become corrupted. By appending all new operations to the end of the file, existing data remains physically safe on disk. The worst case of a crash is a partial line at the end, which the engine is designed to isolate and discard on reboot.

Engine Architecture & Data Flow

WRITE FLOW
POST /events (JSON payload)
Append to events.log (Immutable Disk)
Update memory index (ID -> offset, length)
READ FLOW (O(1) Seek)
GET /events/{id}
Lookup offset & length in RAM index
f.seek(offset) + f.read(length)

API Endpoints & Modules

POST `/events`: Stamping UUID & ISO timestamp, appending encoded payload, updating the index, returning response.

GET `/events/{id}`: Querying the RAM index, jumping directly to byte offsets using `f.seek()`, reading the exact length, decoding JSON, returning response.

GET `/stats`: Returns active event count and file byte size on disk.

Technical Challenge: The Unicode Bug

The Bug: When calculating index offsets, measuring character length (e.g. len(json_str)) worked fine for ASCII text (1 char = 1 byte). However, if an event contained non-latin unicode characters (like é, ü, or emojis), those characters occupied multiple bytes. Character length was shorter than byte length, throwing off all subsequent offset values. Jumping with f.seek() landed mid-character, resulting in parsing garbage.

The Solution: Pre-encoding the JSON string to UTF-8 bytes before calculating the length, guaranteeing index lengths correspond precisely to the file's byte offsets. Additionally, since Python internally buffers reads (causing f.tell() to incorrectly return future values), the startup recovery loop tracks byte offsets manually by iterating through raw byte lines.

python store.py 
# Stamp, Serialize & Encode to UTF-8
event = {
    "id": str(uuid.uuid4()),
    "createdAt": datetime.now(timezone.utc).isoformat(),
    **body,
}
# Encode first to measure exact byte length
line = (json.dumps(event, ensure_ascii=False) + "\n").encode("utf-8")
length = len(line) 

# Startup Recovery: Byte-Safe Rebuilding
offset = 0
with open(self.log_path, "rb") as f:
    for line in f:
        length = len(line)
        try:
            event = json.loads(line.decode("utf-8"))
            self.index[event["id"]] = {
                "offset": offset, 
                "length": length
            }
        except Exception:
            # Skip torn/corrupt lines from crashes
            pass
        finally:
            offset += length # Track byte position

Low-Level Data Mechanics

Building the append-only event store demystified databases for me. I learned that durability isn't magic—it's about write-ahead logs (WAL) protecting data from crash corruption at the byte level. Understanding how Python's internal file buffers interact with OS file cursors shifted how I write file I/O operations.

Pragmatic Optimization & Caching

Working on Insighta taught me how to scale without adding infrastructure overhead.
